Create the Namespace

Isolate the demo in its own logical space
kubectl create namespace otel-demo
ℹ
What is a Namespace? A Kubernetes Namespace is a logical isolation mechanism. It lets you organize resources (Pods, Services, ConfigMaps) into independent groups, apply separate access policies and simplify cleanup.
# Verify creation
kubectl get namespace otel-demo

Install the Helm chart

Deploy all microservices to the cluster

Standard install:

helm install my-otel-demo open-telemetry/opentelemetry-demo \
  --namespace otel-demo \
  --wait

With custom values:

helm install my-otel-demo open-telemetry/opentelemetry-demo \
  --namespace otel-demo \
  --values my-values.yaml \
  --wait
ℹ
Command breakdown:
  • my-otel-demo — release name (can be anything)
  • open-telemetry/opentelemetry-demo — chart to install
  • --namespace otel-demo — deploys into the created namespace
  • --wait — blocks until all Pods are Ready
⚠
Install time: The first run may take 5–10 minutes while container images are pulled.

Access the services

Port-forward to reach services from your local machine
ℹ
What is port-forward? kubectl port-forward creates a TCP tunnel between your local machine and a cluster Service. Traffic to the local port is forwarded to the Pod. Ideal for development and debugging, not for production.
# Frontend — http://localhost:8080
kubectl port-forward -n otel-demo svc/my-otel-demo-frontend 8080:8080

# Jaeger (Traces) — http://localhost:16686
kubectl port-forward -n otel-demo svc/my-otel-demo-jaeger-query 16686:16686

# Grafana (Dashboards) — http://localhost:3000  (admin/admin)
kubectl port-forward -n otel-demo svc/my-otel-demo-grafana 3000:80

# Prometheus — http://localhost:9090
kubectl port-forward -n otel-demo svc/my-otel-demo-prometheus 9090:9090

# Locust (Load) — http://localhost:8089
kubectl port-forward -n otel-demo svc/my-otel-demo-loadgenerator 8089:8089
⚠
Open a separate terminal for each port-forward, or append & to run them in the background.

Virtual Network (VCN)

OKE requires a Virtual Cloud Network with subnets
✅
Recommended — Quick Create: When creating the cluster in Step 4, select "Quick Create". OCI will automatically generate the VCN with all required subnets and security lists. You do not need to do this step manually.

To create the VCN manually via CLI:

# Get root compartment OCID
oci iam compartment list --all \
  --query "data[?\"lifecycle-state\"=='ACTIVE'].id | [0]"

# Create VCN
oci network vcn create \
  --compartment-id <COMPARTMENT_OCID> \
  --display-name otel-demo-vcn \
  --cidr-block 10.0.0.0/16 \
  --dns-label oteldemo

Create the OKE cluster

Oracle Kubernetes Engine — free control plane, ARM Always Free nodes

Option A — From the OCI Console (recommended):

  1. Hamburger menu → Developer Services → Kubernetes Clusters (OKE).
  2. Click "Create cluster" → select "Quick create" → Launch workflow.
  3. Configure the following values:
    FieldRecommended value
    Nameotel-demo-cluster
    Kubernetes versionLatest available
    VisibilityPublic endpoint (for kubectl access)
    ShapeVM.Standard.A1.Flex (ARM — Always Free)
    OCPUs per node2
    Memory per node12 GB
    Number of nodes2 (total: 4 OCPUs / 24 GB = Always Free limit)
  4. Click "Next" → "Create cluster".
  5. Wait ~5–10 minutes until the status shows Active.
⚠
Always Free ARM limit: Exactly 4 OCPUs + 24 GB RAM total. Use 2 nodes × 2 OCPUs / 12 GB to stay within the free tier.

Option B — Via CLI:

# Create OKE cluster
oci ce cluster create \
  --compartment-id <COMPARTMENT_OCID> \
  --name otel-demo-cluster \
  --vcn-id <VCN_OCID> \
  --kubernetes-version v1.30.1 \
  --service-lb-subnet-ids '["<SUBNET_OCID>"]' \
  --endpoint-subnet-id <SUBNET_OCID> \
  --endpoint-public-ip-enabled true

# Create ARM Always Free node pool
oci ce node-pool create \
  --cluster-id <CLUSTER_OCID> \
  --compartment-id <COMPARTMENT_OCID> \
  --name otel-demo-pool \
  --node-shape VM.Standard.A1.Flex \
  --node-shape-config '{"ocpus": 2, "memoryInGBs": 12}' \
  --size 2 \
  --node-image-name "Oracle-Linux-8.x-aarch64-2024" \
  --placement-configs '[{"availabilityDomain":"<AD>","subnetId":"<SUBNET_OCID>"}]'

Get the OKE cluster kubeconfig

Connect kubectl to the Oracle Cloud cluster
# Get cluster OCID
oci ce cluster list \
  --compartment-id <COMPARTMENT_OCID> \
  --query "data[?name=='otel-demo-cluster'].id | [0]" \
  --raw-output

# Generate and merge kubeconfig
oci ce cluster create-kubeconfig \
  --cluster-id <CLUSTER_OCID> \
  --file $HOME/.kube/config \
  --region us-ashburn-1 \
  --token-version 2.0.0 \
  --kube-endpoint PUBLIC_ENDPOINT
ℹ
  • --file $HOME/.kube/config — merges the OKE context into the existing kubeconfig
  • --token-version 2.0.0 — short-lived tokens, more secure
  • --kube-endpoint PUBLIC_ENDPOINT — connects via the public endpoint

Install OTel Demo with ARM tuning

The chart supports aarch64 natively since v0.28+

Create oci-values.yaml optimized for ARM Always Free nodes:

# oci-values.yaml — tuned for 4 OCPUs / 24 GB ARM Always Free
default:
  resources:
    requests: { cpu: "50m", memory: "64Mi" }
    limits:   { cpu: "200m", memory: "256Mi" }

components:
  frontend:
    resources:
      requests: { cpu: "200m", memory: "256Mi" }
      limits:   { cpu: "500m", memory: "512Mi" }
  checkoutservice:
    resources:
      requests: { cpu: "100m", memory: "128Mi" }
  cartservice:
    resources:
      requests: { cpu: "100m", memory: "128Mi" }

opentelemetry-collector:
  resources:
    requests: { cpu: "200m", memory: "256Mi" }
    limits:   { cpu: "500m", memory: "512Mi" }

prometheus:
  server:
    resources:
      requests: { cpu: "200m", memory: "512Mi" }

grafana:
  resources:
    requests: { cpu: "100m", memory: "256Mi" }

Install the chart:

helm install my-otel-demo open-telemetry/opentelemetry-demo \
  --namespace otel-demo \
  --values oci-values.yaml \
  --wait \
  --timeout 15m
⚠
Why --timeout 15m? On ARM Always Free nodes image pulls can take longer. The extended timeout prevents Helm from cancelling the deployment prematurely.

Create the kind cluster

Local Kubernetes cluster ready in ~60 seconds

Create a kind-config.yaml configuration file to tune resources:

# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    kubeadmConfigPatches:
      - |
        kind: InitConfiguration
        nodeRegistration:
          kubeletExtraArgs:
            node-labels: "ingress-ready=true"
    extraPortMappings:
      - containerPort: 80
        hostPort: 80
        protocol: TCP
      - containerPort: 443
        hostPort: 443
        protocol: TCP
  - role: worker
  - role: worker

Create the cluster with that configuration:

# Create cluster (~60 seconds)
kind create cluster \
  --name otel-demo \
  --config kind-config.yaml

# Verify the cluster is running
kubectl cluster-info --context kind-otel-demo
kubectl get nodes
✅
You should see 3 nodes (control-plane + 2 worker) in Ready state.
ℹ
Tip — multiple contexts: If you have other clusters configured, make sure to use the correct context: kubectl config use-context kind-otel-demo

Parse useful information from Logs

Extract structured fields with Parsing Rules in Coralogix

OTel Demo logs arrive in JSON format. Coralogix allows extracting specific fields via Parsing Rules to turn text into queryable, filterable fields.

Configure a Parsing Rule in Coralogix:

  1. In the console, go to Data Flow → Parsing Rules.
  2. Click "New Rule Group".
  3. Set the scope: Application = otel-demo, Subsystem = *.
  4. Add a rule of type JSON Extract for the text field and map the extracted fields.
  5. Save and verify in Explore → Logs that the fields appear as columns.
ℹ
Example — Regex Parsing Rule to extract http.method, http.status_code and service.name from the log body:
# Example regular expression for frontend logs
(?P<http_method>GET|POST|PUT|DELETE|PATCH)\s(?P<http_path>\/[^\s]*)\s.*?status=(?P<http_status>\d{3})
💡
Recommended fields to parse from the OTel Demo:
  • service.name — name of the originating microservice
  • http.method + http.route + http.status_code — HTTP requests
  • span_id + trace_id — correlation between logs and traces
  • exception.type + exception.message — application errors
  • k8s.pod.name + k8s.namespace.name — infrastructure context

Verify the result in Explore → Logs using the extracted field:

# Example query in Lucene (DataPrime also available)
http_status:5* AND service_name:checkoutservice

Apply Enrichments

Add additional context to ingested telemetry

Enrichments in Coralogix add contextual fields to logs and traces in real time, based on existing values or external lookup tables.

Enrichment types applicable to the OTel Demo:

Enrichment TypeSource fieldAdded dataUse case
Geo-enrichmenthttp.client_ipCountry, city, ASNView geographic distribution of users
Custom Lookup Tableservice.nameOwner team, tier, SLAAttribute incidents to teams quickly
AWS enrichmentk8s.node.nameInstance type, AZ, regionCorrelate failures with AWS infrastructure
Security enrichmenthttp.client_ipIP reputation, threat scoreDetect malicious IPs in demo traffic

Configure a Custom Lookup Table enrichment:

  1. Go to Data Flow → Enrichments → Custom Enrichment.
  2. Upload a CSV with the structure: service_name,team,tier,sla_minutes.
  3. Configure the join field: service.name.
  4. Enable the enrichment and apply it to the otel-demo application.

Create a metric with Events2Metrics

Convert logs and traces into long-term metrics for retention and alerting
ℹ
What is Events2Metrics? Events2Metrics converts individual logs or spans into aggregated metrics (counter, gauge, histogram) stored permanently at low cost. Ideal for retaining KPIs beyond the log retention window.

Example: HTTP error rate metric per service

  1. Go to Data Flow → Events2Metrics and click "Add Metric".
  2. Select source Spans (traces).
  3. Configure the fields:
FieldValue
Metric nameotel_demo_http_errors_total
Metric typeCounter
Filterhttp.status_code >= 400
Dimensions (labels)service.name, http.route, http.status_code
Applicationotel-demo

Second example: Checkout P95 latency

FieldValue
Metric nameotel_demo_checkout_duration_ms
Metric typeHistogram
Value fieldduration_ms
Filterservice.name:checkoutservice
Dimensionsservice.name, span.name
✅
After 2–5 minutes, the metrics will appear in Explore → Metrics and you can query them with PromQL: rate(otel_demo_http_errors_total[5m])

Configure Proactive Alerts

Early detection of problems before they impact users

Go to Alerts → New Alert and create the following alerts to monitor the OTel Demo:

AlertTypeConditionSeverityPurpose
High 5xx error rateMetric Alertrate(otel_demo_http_errors_total{status_code=~"5.."}[5m]) > 0.1CriticalDetect server failures
Elevated P95 latencyMetric Alerthistogram_quantile(0.95, rate(http_server_duration_milliseconds_bucket[5m])) > 2000HighPerformance degradation
Pod in CrashLoopBackOffLog AlertLog text contains CrashLoopBackOffCriticalApplication failure
Unhandled exceptionLog AlertSeverity = ERROR AND exception.type exists — more than 10 in 5 minHighFrequent application errors
Checkoutservice with no trafficMetric Alert (absence)rate(http_server_duration_milliseconds_count{service="checkoutservice"}[10m]) == 0HighCritical service down
Memory usage > 85%Metric Alert(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) > 0.85MediumOOM risk on nodes
OTel Collector with no dataMetric Alert (absence)No data from the exporter for 10 minCriticalBroken telemetry pipeline

Configure notifications for alerts:

  1. In each alert, go to the Notify section.
  2. Choose the channel: Email, Slack, PagerDuty, Webhook, etc.
  3. Configure the Notification Group (who receives which severity).
  4. Enable Alert Suppression to avoid flapping on noisy alerts.
